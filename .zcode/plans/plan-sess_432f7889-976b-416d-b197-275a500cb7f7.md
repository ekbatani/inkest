# Share a project between several users

## Design (per your choices)
- **Add-by-email**: owner types an existing user's email in a Share dialog; access is granted immediately (no email infrastructure exists, none is added).
- **Roles**: `viewer` (read-only) and `editor` (edit content, create/edit child notes & tasks). Only the **owner** manages sharing and can delete the project.
- **Attachments follow project access**: members can read files on notes inside the shared project; editors can upload.
- **Share root rule**: a "project" is a `notes` row with `type: "project"`. Sharing attaches to the *outermost* project in a parent chain and covers its whole subtree (sub-projects, child notes, task notes, attachments). Access to any note = walk up to the outermost project ancestor (or self); `owner` if `notes.userId` is you, else the `project_members` row's role, else no access. Notes outside any project remain owner-only.

## 1. Schema — `src/server/db/schema.ts` + migration
New table (follows existing table conventions):
```ts
project_members: id, project_id (FK notes, cascade), user_id (FK users, cascade),
role ("viewer"|"editor", default "viewer"), added_by_user_id (FK users, set null),
created_at
indexes: unique(project_id, user_id), index(user_id), index(project_id)
```
Then `bun run db:generate`, commit the migration, `bun run db:migrate`. (Note: `drizzle/0005_sweet_firedrake.sql` is a pre-existing orphaned file — untouched.)

## 2. Access module — new `src/server/projects/access.ts`
- `resolveProjectAccess(noteId, userId)` → `{ note, projectId, role: "owner"|"editor"|"viewer" } | null`. Loads the note by id (no user filter), rejects deleted, walks `parentId` up to the outermost `type:"project"` ancestor (visited-set + depth cap ~50 for cycle safety); owner check, then membership lookup.
- `requireView` / `requireEdit` helpers throwing the existing error codes (`UNAUTHORIZED` / not-found semantics — don't leak existence to non-members).
- Pure `findShareRoot(parentMap, noteId)` helper extracted so it's unit-testable without a DB.

## 3. Notes service — `src/server/notes/service.ts` (the core scoping change)
Keep every existing signature; swap `eq(notes.userId, me)` ownership for access-aware logic:
- `getNoteById`: fetch by id + `isNull(deletedAt)`, then gate through `resolveProjectAccess`.
- `listNotes`:
  - `type:"project"` (Projects page): `or(ownerScope, inArray(notes.id, sharedProjectIdsFor(me)))`.
  - `parentId` queries: check access on the parent once; if accessible, run the child query scoped to the *parent's* owner ids (children are owner-stamped); if not, return `[]`.
  - Default/global notes listing stays owner-only — shared content is reached via Projects and links (stated product behavior).
- `createNote` with `parentId`: require editor+ on the parent; stamp the new note with the **parent's** `userId`/`workspaceId` (subtree stays homogeneous under the project owner). Generalize `assertValidParentAssignment` to take the tree-owner scope instead of the acting user's; same for sort-order sibling queries. `indexDocument` uses the note's real owner ids.
- `updateNote`: fetch current by id (no user filter), require editor+; UPDATE by id + `isNull(deletedAt)` (authorization comes from the access check, not the WHERE clause). Content/status/priority edits → editor+; `type`/`parentId` changes → owner-only (no reshaping shared trees). Fix `indexDocument` to pass the note's owner ids, not the acting user's workspace.
- `archiveNote`/`unarchiveNote`/`deleteNoteSoft`: owner-only for the share-root project itself; editor+ for descendants. `togglePinned`: owner-only no-op otherwise. `moveNoteInTree`: editor+ within the tree. `getBacklinks` already uses the target's owner scope — unchanged.

## 4. Projects domain — new `src/server/projects/{validation,service,actions}.ts`
- `validation.ts`: `shareRoleEnum`, `addMemberSchema` (email + role), `updateMemberSchema`, `MAX_PROJECT_MEMBERS = 20` — vault-service inline-schema pattern.
- `service.ts`: `listProjectMembers` (view access; join `users` for name/email/image + owner row), `addProjectMember` (owner-only; target must be a share-root project; email resolves via existing user lookup; rejects owner's own email; upserts role if already a member), `updateProjectMemberRole`, `removeProjectMember` (owner-only). Each mutation writes an `audit_logs` row (`project.member_added|role_changed|removed`) following the vault-service audit pattern.
- `actions.ts` ("use server"): thin wrappers, `safeParse` → `{ error, code }` returns (auth-actions pattern), `revalidatePath("/projects/" + id)` + `/projects`.

## 5. Attachments — `src/server/attachments/service.ts`
- `serveAttachment`: owner fast-path stays; otherwise if the attachment has a `noteId`, `resolveProjectAccess` grants read to any member role. `Cache-Control: private, no-store` untouched — data never becomes public.
- Upload attaching to a note: require editor+ on that note (owner-only otherwise, as today).

## 6. UI
- New `src/components/projects/project-share-dialog.tsx` (client): Dialog per `journal-template-modal` pattern; member rows (Avatar, name/email, role `Select`, remove button) + add form (email `Input`, role `Select`, Add button); direct action imports + `router.refresh()` + `toast` errors per the dominant pattern. Logical CSS properties only (RTL); keyboard access from the Base UI primitives.
- `src/app/(app)/projects/[id]/page.tsx`: fetch members + current role server-side; header gains an AvatarGroup preview + "Share" button (owner) or role badge (member); viewer mode hides Subproject/Edit, renders the title read-only, and passes `canEdit={false}` to `ProjectTaskNotesPanel` (disable drag/create).
- `src/app/(app)/projects/page.tsx`: shared projects already flow in via `listNotes`; add a small "Shared" badge on projects not owned by the viewer.
- Note editor route (`/notes/[id]`, reached via "Edit as note"): render read-only preview for viewers instead of the editor; editors work through the access-aware service.
- No auth-gate changes needed — `/projects` is already behind `withAuth`.
